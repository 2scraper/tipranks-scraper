# Contributing

1. Fork, branch, make your change.
2. `pip install -r requirements-playwright.txt` (or `-selenium` / `-puppeteer`) and run `python3 smoke_test.py` — it must pass with **no** engine installed at all, so if you're only testing one engine, that's still a meaningful run.
3. **If you touched `tipranks_parser.py`: read its module docstring first.** It is the only file in this repo carrying tipranks.com knowledge, and it separates CONFIRMED facts (from real live captures) from what's explicitly out of scope or never observed. If you have a real capture that confirms or corrects something in it, save it under `tests/fixtures/`, update the parser to match, and update the docstring. Don't remove a CONFIRMED note without a capture backing the change up.
4. **Keep the "all analysts" and "best analysts" consensus scopes separate.** `TickerRating.consensus_*` and `best_consensus_*` are two different, real analyst populations from tipranks.com's own `analystRatings.all` and `analystRatings.best`. A PR that merges them into one field will be rejected on sight.
5. Every field on `TickerRating` is independently optional — a real payload can have a price target with no consensus label, or no `analystRatings` at all (see `tipranks_parser.py`'s docstring for the confirmed live examples). New parsing code must not assume that seeing one field implies seeing another.
6. Keep the three engines behaving identically: same exit codes, same `TickerRating` schema, same CLI flags. If one needs to diverge (see `selenium_scraper.py`'s not-found-detection difference for an example), say why in a comment, and in that engine's own module docstring.
7. Open a PR. CI runs the offline suite on two Python versions, one `engine-smoke` job per engine (each in its own virtualenv), and builds/exercises the Docker image — see `TESTING.md`. A daily `canary` job runs a real, unauthenticated scrape against the live site; it needs no secret to run (this site's data is free and public), but a live-site block from a datacentre IP is a reported warning there, not a merge-blocking failure — see that workflow's own comments.

Bug reports and feature requests: open an issue. Please include the exact command you ran and the `.meta.json` sidecar from the run (or note that none was written — that's itself informative, see `output_writer.finish_run`'s docstring), not just a description. If you're reporting that a ticker came back empty, attaching the actual `payload.json` response (or noting the HTTP status you got) is the single most useful thing you can add — real, confirmed site behavior is the only thing this repo's parser is allowed to encode.
